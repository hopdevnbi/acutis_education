10. MSSQL Readiness
-------------------
SQL Server may take time to start in Bitbucket.

Do NOT rely on a fixed arbitrary sleep only.

Add a portable readiness mechanism.

Preferred:
a small Node/TypeScript script using existing `mssql` dependency.

Example responsibility:
- repeatedly attempt connection
- SELECT 1
- bounded retries
- clear timeout
- no password logging
- exit non-zero on failure

Possible file:
scripts/wait-for-mssql.ts
or
test/database/wait-for-mssql.ts

Choose a location that reflects CI/test infrastructure.

Requirements:
- portable Linux/Windows Node script
- no WSL dependency
- no shell-specific syntax
- no new dependency if existing `mssql` suffices
- no secret output

Add package script such as:
ci:wait-for-mssql

or another clear name.

11. Readiness Script Safety
---------------------------
The wait script should:

- load connection settings from env
- not require `.env`
- validate required fields
- use short connection timeout
- retry at reasonable interval
- cap total wait time
- print only non-secret diagnostic info
- close each pool/connection cleanly

Do not print full connection config.

12. Database Test Step
----------------------
Add a reusable pipeline step, e.g.:

Database Tests

It should:

1. npm ci
2. wait for MSSQL
3. run:
   npm run quality:full

However, note:
`quality:full` internally re-runs `quality`.

This may duplicate Quality step work.

Evaluate two options:

A. Simplicity:
Database Tests step runs `npm ci` + `npm run quality:full`
- duplicates fast quality
- easiest to reason about

B. Efficiency:
Database Tests step runs only:
- test:db:migrations
- test:integration
- test:e2e:db

Preferred initial v1:
Choose maintainability over optimization.

If using `quality:full`, clearly document duplication.

If using DB-only scripts, ensure full gate semantics remain clear.

Do not invent a new complex task runner.
