5. Critical Cycle Design for Clone
----------------------------------
CURRICULUM #001 suggested Curriculum may orchestrate LearningContent copy.

But current dependency target is:
LearningContentModule -> CurriculumModule

That means CurriculumModule must NOT import LearningContentModule.

Therefore deep clone must be designed without creating:
CurriculumModule <-> LearningContentModule

Preferred approaches:

A. Create a thin application/orchestration module/provider at AppModule layer
that depends on both modules and coordinates clone/publish.

OR

B. Let CurriculumService clone structure and return lesson mapping,
then LearningContentService clones content in a separate orchestration command
owned by a higher-level application service.

Do NOT use forwardRef.

Choose the cleanest minimal design and document.

24. Publish Transaction
-----------------------
Need atomic behavior:

- lock curriculum/version
- validate DRAFT
- validate all structure/content
- set version status PUBLISHED
- set publishedAt=now
- set publishedByUserId
- set curriculum.currentPublishedVersionId = versionId

If policy is one current published:
previous published remains PUBLISHED historically or becomes ARCHIVED?

Selected approach:
- previous PUBLISHED version may remain PUBLISHED historical until superseded/assignment policy
OR
- previous current PUBLISHED becomes ARCHIVED atomically.

Choose consistent model.

Preferred simpler:
when publishing new current version:
previous current PUBLISHED -> ARCHIVED
new DRAFT -> PUBLISHED
currentPublishedVersionId -> new version

This gives exactly one current PUBLISHED pointer and preserves history.

Document carefully.

28. Deep Clone Semantics
------------------------
Transactionally:

1. lock curriculum
2. compute next versionNumber
3. create DRAFT version
4. copy topics with new IDs, same metadata/order/code
5. copy lessons with new IDs
6. preserve canonicalLessonKey
7. map oldTopicId -> newTopicId
8. copy lesson content rows to new lesson IDs
9. recompute/preserve contentHash exactly
10. return new draft summary

29. Cross-Module Clone Atomicity
--------------------------------
CRITICAL.

Because CurriculumModule and LearningContentModule own different repos,
do not fake a distributed transaction with unrelated repositories.

In modular monolith with same MSSQL/TypeORM DataSource:
a higher-level application service may own a QueryRunner transaction and pass EntityManager-scoped public operations to both module-owned services.

But module ownership must remain respected:
- each module service performs writes to its own entities
- orchestrator controls transaction boundary
- no direct cross-repo manipulation

If this pattern is too invasive:
design an application orchestration service inside a dedicated small module.

No forwardRef.
