6. MODULE TYPE
--------------
Strong default:
stateless orchestration/read-model facade.

It should compose public APIs from:
- Class
- Enrollment
- Student
- Practice
- Learning Progress
- Exam
- possibly Curriculum/Localization

It should NOT own:
- class data
- enrollment data
- progress rows
- practice sessions
- exam attempts
- guardian links
- catechist assignments

Prefer ZERO new business tables.

If audit recommends a table:
must justify why a durable read-model/cache is necessary.
MVP preference = no table.

12. CATECHIST CONTEXT API

Potential fields:

- academic year / catechism level identifiers

-----------------

Recommend exact approach.

22. ROLE IS NOT SCOPE
---------------------
Non-negotiable:

PARENT role alone != child access.
CATECHIST role alone != class access.

Parent:
persisted Guardian->Student relationship.

Catechist:
active Catechist->Class assignment.

Every orchestration method must enforce server-side scope.

Bad:

PracticeService
LearningProgressService
ExamService

Determine whether there are:
- class aggregate methods
- batch enrollment summary methods

If missing:
recommend narrow batch public APIs in owning modules.

Strong rule:
orchestration must not loop DB-heavy service calls per student if a bounded batch API can be added.
