RULE CONTENT
============
The rule must clearly encode all of the following.

1. DEFAULT MODE = CODE FIRST
----------------------------
For normal implementation prompts, prioritize:
- production functions
- services
- controllers
- endpoints
- DTOs
- entities
- migrations
- interfaces/contracts
- module wiring
- seed code when requested
- Postman artifacts when requested
- unit test files
- integration test files
- DB e2e test files
- documentation/report files

Complete the requested code surface first.

Do not spend significant time executing validation commands.

2. TESTS MUST STILL BE WRITTEN
------------------------------
Implementation prompts MUST still create/update appropriate test files:
- `.spec.ts`
- integration specs
- DB e2e specs
- security/denial tests
- module-boundary tests

Tests are part of implementation.

However, by default:
DO NOT EXECUTE THEM.

The purpose is to build the complete endpoint/function surface quickly, then validate later during FE integration / stabilization.

3. DEFAULT: DO NOT RUN VALIDATION COMMANDS
------------------------------------------
Unless the user explicitly asks to validate/run checks, DO NOT run:
- `npm test`
- Jest commands
- unit tests
- integration tests
- DB e2e tests
- `npm run test:*`
- `npm run quality`
- `npm run quality:full`
- `npm run lint`
- `npm run typecheck`
- `npm run build`
- `npm run format`
- `npm run format:check`
- `npm audit`
- migrations against a live/test database
- DB reset/prepare commands
- seed execution
- Postman/Newman execution

Do not treat unexecuted tests as failures.

4. DEFAULT: DO NOT OPERATE DOCKER
---------------------------------
Unless explicitly requested by the user, DO NOT:
- `docker compose up`
- `docker compose down`
- start/stop/restart containers
- start Docker daemon
- build Docker images
- inspect container logs for validation
- wait for MSSQL/container health
- troubleshoot Docker environment
- create Windows/WSL path workarounds solely for testing

Docker/runtime validation is deferred.

5. DO NOT BLOCK IMPLEMENTATION ON LOCAL ENVIRONMENT
---------------------------------------------------
If:
- Docker is down
- MSSQL is unavailable
- `.env` has a missing runtime-only value
- registry/network is unavailable
- test DB is not running
- local Docker/WSL paths differ

do NOT stop normal business implementation unless the missing information is genuinely required to design/code the feature correctly.

Report environment issues as deferred validation concerns, not implementation blockers.

6. MIGRATIONS
-------------
When schema changes are required:
- WRITE migration files correctly
- WRITE entity/schema changes
- WRITE tests for migrations

But do not execute migrations against DB by default.

Never edit an already-landed migration if project architecture requires a new migration.

7. REPORTING LANGUAGE
---------------------
Reports MUST distinguish:

IMPLEMENTATION STATUS
from
VALIDATION STATUS

Use wording such as:
- `IMPLEMENTED: YES`
- `TESTS WRITTEN: YES`
- `TESTS EXECUTED: NO — deferred by Fast Implementation Mode`
- `DB VALIDATION: NOT RUN — deferred`
- `QUALITY:FULL: NOT RUN — deferred`
- `DOCKER: NOT RUN — deferred`
- `NPM AUDIT: NOT RUN — deferred`

Never write `FAIL` merely because a command was intentionally not executed.

8. READINESS / PROMPT GATES
---------------------------
During Fast Implementation Mode, moving to the next implementation prompt should be based primarily on:
- requested code exists
- architecture matches design
- contracts are complete
- security/scope logic is implemented
- tests/specs are written
- no known BLOCKER/HIGH defect from code inspection

Do NOT require runtime test execution to advance between implementation prompts.

Runtime validation gates are intentionally deferred to a later stabilization/integration phase.

9. STATIC CODE INSPECTION
-------------------------
Cursor should still inspect the edited code carefully before finishing:
- imports
- obvious TypeScript syntax errors
- route duplication
- DTO mismatches
- missing exports
- circular imports
- wrong module wiring
- obvious entity/migration mismatch
- scope/permission bypass
- N+1 patterns visible from code
- accidental entity leakage

Fix obvious problems by code review.

Do not launch a large command/test loop just to verify.

10. ARCHITECTURE / SECURITY ARE NOT DEFERRED
--------------------------------------------
Fast mode does NOT mean careless implementation.

Still enforce immediately:
- module ownership
- public API boundaries
- no foreign repository/entity access
- no unnecessary `forwardRef`
- RBAC + scope separation
- actor-specific `/me` semantics
- child/minor privacy
- no PII leakage
- historical data safety
- idempotency/concurrency design where required
- deterministic API contracts
- pagination/batching/N+1 design
- no production secrets

These are CODE REVIEW gates and remain mandatory.

11. USER OVERRIDE
-----------------
If the user explicitly says:
- run tests
- validate
- run Docker
- run migrations
- check quality
- perform regression
- verify npm audit

then execute exactly the requested validation scope.

Otherwise remain in Fast Implementation Mode.

12. FUTURE STABILIZATION PHASE
------------------------------
Document that after endpoint/function implementation is broadly complete, the project will enter a separate:

FE INTEGRATION / STABILIZATION / VALIDATION PHASE

During that phase, tests and validation will be run incrementally:
- compile/typecheck
- unit
- integration
- DB e2e
- migrations
- Docker
- API manual/Postman
- FE contract integration
- regression/security fixes

Do not perform that stabilization early by default.
