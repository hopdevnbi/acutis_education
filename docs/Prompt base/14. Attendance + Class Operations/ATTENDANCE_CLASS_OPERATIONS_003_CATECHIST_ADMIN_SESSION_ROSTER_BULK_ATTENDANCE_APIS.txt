CREATE SESSION
--------------
POST /api/v1/classes/:classId/sessions

Input:
- title? max 128
- startsAt ISO
- endsAt ISO

Server-derived:
- classId from route
- parishId from class
- academicYearId from class
- status SCHEDULED
- actor IDs from auth context

Rules:
- class exists
- class status ACTIVE
- endsAt > startsAt
- permission + actor scope
- transaction: create session + freeze roster

Roster freeze:
- batch ACTIVE enrollments for class
- batch student names
- no N+1

Empty roster:
may still create session; document behavior.

STAFF SCOPE
-----------
CATECHIST:
- class-sessions.manage / attendance.manage
- ACTIVE assignment to target class
- role alone is never enough

PARISH_ADMIN:
- own parish scope + permission

SUPER_ADMIN:
- global + permission

PARENT/STUDENT:
- staff endpoints forbidden in #003

Never trust client parish/user/student IDs for scope.

LIST SESSIONS
-------------
GET /api/v1/classes/:classId/sessions

Query:
- page default 1
- limit default project convention, max 50
- from?
- to?
- status?

Deterministic default:
startsAt DESC + id tie-breaker.

Return compact DTO + pagination.

If rosterCount/markedCount can be obtained with bounded grouped queries, include.
Otherwise omit from list and expose on detail/attendance.

No per-session count loop.

GET SESSION
-----------
GET /api/v1/class-sessions/:sessionId

Authorize by session class/parish scope.

Return compact session data.
Optional bounded counts okay.

No learner PII.

UPDATE SESSION
--------------
PATCH /api/v1/class-sessions/:sessionId

Only SCHEDULED.

Editable:
- title
- startsAt
- endsAt

Do not allow:
- classId
- parishId
- academicYearId
- status
- createdBy

Changing time while SCHEDULED = reschedule behavior.
No RESCHEDULED status.

CANCEL
------
POST /api/v1/class-sessions/:sessionId/cancel

Only:
SCHEDULED -> CANCELLED

Set cancelledAt UTC.
After cancel:
- no attendance writes
- no roster refresh
- no metadata edits
- keep existing marks
- excluded from future summary

Second cancel/non-SCHEDULED -> 409.

COMPLETE
--------
POST /api/v1/class-sessions/:sessionId/complete

Only:
SCHEDULED -> COMPLETED

Set completedAt UTC.
After complete:
- attendance locked
- roster locked
- metadata locked

MVP may complete with UNMARKED learners.
Expose rosterCount / markedCount / unmarkedCount where appropriate.
Do not block completion solely because unmarked exist.

ROSTER REFRESH
--------------
POST /api/v1/class-sessions/:sessionId/roster/refresh

Allowed only:
- SCHEDULED
- zero attendance rows

Flow:
- authorize manage
- batch current ACTIVE enrollments
- batch student names
- transactionally replace roster snapshot

After first mark -> 409.
After completed/cancelled -> 409.

ATTENDANCE GET
--------------
GET /api/v1/class-sessions/:sessionId/attendance

Permission:
attendance.read

Staff only:
assigned Catechist
ParishAdmin own parish
SuperAdmin

Parent/Student -> 403 in #003.

Response:
- compact session
- rosterCount
- markedCount
- unmarkedCount
- items:
  - enrollmentId
  - studentId
  - displayName
  - status nullable
  - note nullable
  - markedAt nullable

No DOB/email/phone/address/guardian data.

Stable sort:
displayName then enrollmentId.

BULK ATTENDANCE PUT
-------------------
PUT /api/v1/class-sessions/:sessionId/attendance

Permission:
attendance.manage

Payload:
{
  "records": [
    {
      "enrollmentId": "...",
      "status": "PRESENT|ABSENT|LATE|EXCUSED",
      "note": "..."
    }
  ]
}

Rules:
- session exists
- session SCHEDULED
- actor can manage class/session
- duplicate enrollmentId in payload => 400
- every enrollmentId must be in frozen roster
- note max 500
- transaction all-or-nothing
- omitted learners remain UNMARKED
- upsert by (sessionId,enrollmentId)
- retry same payload is safe

Server-derived:
- studentId from roster
- markedBy/updatedBy from actor
- markedAt UTC

Do NOT accept client:
studentId
userId
parishId
classId
markedBy
markedAt

NOTE POLICY
-----------
Optional note max 500.
No pastoral/confessional semantics.
Never log note body.
Do not require note for ABSENT/EXCUSED unless project requirement says so.

ERROR CONTRACT
--------------
Map consistently:

400:
- malformed UUID/query
- duplicate attendance input
- bad time/status payload

401:
- unauthenticated

403:
- wrong actor/scope
- unassigned Catechist
- cross-parish ParishAdmin

404:
- unknown class/session where safe

409:
- update/cancel/complete non-SCHEDULED
- roster refresh after first mark
- attendance write after complete/cancel

422 or 400:
- enrollment not in frozen roster
Use existing project convention.

Never expose SQL errors.
