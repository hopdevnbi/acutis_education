4. ANSWER IDEMPOTENCY — MANDATORY DECISION
------------------------------------------
Current table:
`exam_attempt_answers`
one mutable current answer row per attempt question.

Prompt #003 explicitly warned:
this cannot provide arbitrary historical replay for multiple old `clientAnswerId` values.

Audit actual columns/indexes and choose exact MVP semantics.

Allowed options:

OPTION A — Stable clientAnswerId per attempt question
- client generates one UUID for the question-answer resource
- every edit reuses same clientAnswerId
- row updates payload/hash
- retry of same latest payload is idempotent
- conflicting replay semantics clearly defined

OPTION B — Latest-request idempotency only
- each edit may use new clientAnswerId
- only latest saved key/hash can be replayed safely
- older request replay after a newer edit returns conflict/stale request
- document Mobile contract clearly

OPTION C — Add history/idempotency table
- ONLY if analysis proves A/B unsafe
- this changes 7-table plan and must be justified as HIGH-level requirement

Strong preference:
remain 7 tables using A or B.

Do NOT claim arbitrary historical request replay unless actually supported.
