ISSUE — RECIPIENT SNAPSHOT IS CURRENTLY POST-COMMIT
----------------------------------------------------
#005A correctly added `registeredRecipientUserIds` to:
- EventUpdatedEvent
- EventCancelledEvent

But current flow is:
1. commit Event mutation
2. query event_registrations
3. publish communication event

This is not an atomic snapshot at the domain-transition boundary.

Race examples:
- Update commits, registrant cancels, then snapshot query runs -> a registrant who was active at update time is omitted.
- Update commits, a new registrant registers, then snapshot query runs -> a registrant who joined after the update receives that historical update.
- Cancel commits, then another registration-state mutation races before snapshot read -> recipient set may not reflect cancellation boundary.

Required correction:
capture `registeredRecipientUserIds` inside the SAME DB transaction as the event update/cancel mutation, return that snapshot from the transaction, then emit event only after commit.

PART C — SIGNIFICANT UPDATE FLOW
--------------------------------
Inside same transaction:

After transaction resolves:
emit EventUpdatedEvent using ONLY returned snapshot data.

Do NOT re-query registrations after commit.
