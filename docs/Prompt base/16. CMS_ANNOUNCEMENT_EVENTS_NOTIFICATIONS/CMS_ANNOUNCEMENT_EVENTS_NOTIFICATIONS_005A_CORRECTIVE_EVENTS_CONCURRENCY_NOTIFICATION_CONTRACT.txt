CORRECTIVE ISSUE 1 — CAPACITY TRANSACTION IS NOT PROVEN RACE-SAFE
==================================================

Current #005 report states:

- registration uses `dataSource.transaction`
- active count is read
- capacity compared
- registration inserted
- "guarantees zero over-subscription races"

A transaction alone under ordinary MSSQL READ COMMITTED does NOT guarantee this.

Two concurrent transactions can both:
1. read activeCount = N
2. see N < capacity
3. both insert
4. exceed capacity

Required correction:

Implement one explicit concurrency-safe MSSQL strategy.

Preferred options:

OPTION A — pessimistic lock event row
-------------------------------------
Within one transaction / QueryRunner:
- SELECT event row using pessimistic write lock
- or MSSQL-compatible UPDLOCK/HOLDLOCK semantics
- then count active REGISTERED + ATTENDED
- then insert/reactivate registration
- commit

All registrations for the same event serialize on the event row.

OPTION B — SERIALIZABLE transaction
------------------------------------
Use SERIALIZABLE isolation for registration transaction.

Need ensure TypeORM/MSSQL implementation is explicit and reliable.

Strong preference:
event-row pessimistic write lock or SERIALIZABLE, whichever matches existing repository conventions cleanly.

Required:
- exact lock/isolation strategy
- code evidence
- concurrency-oriented spec written
- do NOT claim "race safe" from transaction alone

Also verify re-registration of CANCELLED row occurs under same capacity lock.
