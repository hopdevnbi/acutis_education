==================================================
ISSUE — RECIPIENT CHECK-THEN-INSERT RACE
==================================================

#006 correctly has:

notification_recipients UNIQUE(notification_id, recipient_user_id)

and fan-out flow described as:

1. query existing recipients for chunk
2. filter missing user IDs
3. insert missing rows

This is idempotent for sequential retries.

However it is not necessarily concurrency-safe.

Race:

Handler A:
- queries recipient X => missing

Handler B:
- queries recipient X => missing

Handler A:
- inserts X successfully

Handler B:
- attempts insert X
- receives MSSQL unique violation 2601 / 2627

If this exception escapes:
- handler B fails
- concurrent replay is not cleanly idempotent
- partial fan-out retry safety claim is incomplete

DB uniqueness prevents duplicate rows, but application-level fan-out must also treat duplicate insert races as successful reconciliation.

PART B — CONCURRENT UNIQUE-RACE RECOVERY
==================================================

Implement a robust strategy.

Preferred behavior:

For each bounded recipient chunk:

1. normalize + dedupe user IDs
2. query existing recipient IDs
3. derive missing IDs
4. attempt batch insert
5. if MSSQL unique violation 2601 or 2627 occurs:
   - do NOT treat the whole logical fan-out as failed immediately
   - re-query the chunk
   - determine which requested recipients now exist
   - insert only any still-missing recipients
   - if all requested rows exist => treat as success
   - if genuinely missing rows remain, retry those missing rows once using safe bounded logic
   - if non-unique error occurs => rethrow

Do not infinite-loop.

Alternative:
use an MSSQL-safe atomic insert-if-not-exists strategy if cleanly supported by current TypeORM/project conventions.

Do NOT use MERGE unless project already trusts it and there is a strong reason.

Strong preference:
unique-violation recovery + re-query.
