CORRECTIVE ISSUE 1 — EVENT LIFECYCLE / API MISMATCH
==================================================

#001 defines Event lifecycle:

DRAFT
-> PUBLISHED
-> CANCELLED or COMPLETED
-> ARCHIVED

It also states:
- Event publication emits EventPublishedEvent
- Event cancellation emits EventCancelledEvent
- Events can later be archived

However exact Event API inventory currently has only:

GET /events
GET /events/:id
POST /events/:id/registrations
POST /events/:id/registrations/cancel
GET /me/event-registrations
POST /admin/events
PATCH /admin/events/:id
POST /admin/events/:id/cancel
POST /admin/events/:id/checkin

Missing lifecycle APIs:
- publish
- complete
- archive

This is inconsistent with the frozen lifecycle and notification flow.

Required corrective decision:

Either:

OPTION A — explicit lifecycle endpoints:
POST /api/v1/admin/events/:id/publish
POST /api/v1/admin/events/:id/cancel
POST /api/v1/admin/events/:id/complete
POST /api/v1/admin/events/:id/archive

or

OPTION B — PATCH status transitions

Strong preference:
OPTION A, matching CMS/Announcement explicit lifecycle-action routes and avoiding arbitrary status mutation.

Required:
- exact corrected Event API inventory
- exact corrected total route count
- lifecycle transition table
- which transition emits which application event
- whether completing emits notification (probably NO by default)
- whether archiving emits notification (probably NO)
- whether update of significant fields emits EVENT_UPDATED

CORRECTIVE ISSUE 2 — NOTIFICATION IDEMPOTENCY GAP
==================================================

#001 claims notification fan-out idempotency by:

(source_type, source_id, recipient_user_id)

But current proposed persistence defines:

notifications:
- index(source_type, source_id)

notification_recipients:
- unique(notification_id, recipient_user_id)

This does NOT alone prevent replay from:

1. creating a second `notifications` header for same source operation
2. generating a new notification_id
3. inserting another recipient row for same user

Therefore current schema and idempotency statement are inconsistent.

Required corrective design.

Evaluate these approaches:

OPTION A — unique notification operation key
--------------------------------------------
notifications includes:
- idempotency_key
or:
- source_type
- source_id
- notification_type / event_type
- source_version / operation_key if needed

Unique:
(source_type, source_id, notification_type)

Then:
notification_recipients unique(notification_id, recipient_user_id)

Examples:
ANNOUNCEMENT_PUBLISHED + announcementId
EVENT_PUBLISHED + eventId
EVENT_CANCELLED + eventId

Problem:
EVENT_UPDATED may occur multiple legitimate times.

For EVENT_UPDATED need:
- update event operation id
or
- source version
or
- deterministic change version/idempotency key

OPTION B — notification operation/event receipt table
-----------------------------------------------------
Add table:
notification_event_receipts
with unique application event ID.

Then one receipt points to one notification header.

This would increase table count to 11.

OPTION C — application event carries unique eventId
---------------------------------------------------
Extend communication events with:
- eventId
- sourceType
- sourceId
- eventType
- occurredAt

notifications has unique:
event_id

This is likely cleanest and extraction-safe if ApplicationEvents already follows event IDs.

Required:
choose exact approach.

Strong preference:
use a stable unique `eventId` on every communication application event and persist it on `notifications` as unique `source_event_id`.

Then:
- replay of exact application event cannot create duplicate notification header
- recipient unique(notification_id, recipient_user_id) prevents duplicate fan-out rows
- multiple legitimate EVENT_UPDATED events each have distinct eventId

Do NOT overload sourceId as eventId.

PART C — ANNOUNCEMENT PUBLISH IDEMPOTENCY
==================================================

Publishing an already-PUBLISHED announcement:

Choose:
- idempotent return existing state
or
- 409 invalid lifecycle

Even if caller retries after ambiguous HTTP failure:
application event emission must not create duplicate notifications.

Design exact behavior.

Strong preference:
domain transition DRAFT -> PUBLISHED happens once.
Repeated publish after already published returns 409 OR existing state, but notification dedupe is protected independently by stable persisted publish event ID/operation key.

Need explain how application event ID stays stable across retry.

Possible:
- persist `published_event_id` on announcement
or
- derive deterministic UUID from announcementId + publication generation
or
- create event ID inside transaction and retain it

Do not assume random UUID regenerated on retry is idempotent.

PART D — EVENT PUBLISH / UPDATE / CANCEL IDEMPOTENCY
==================================================

Define stable operation identity for:

EVENT_PUBLISHED:
one per event publication

EVENT_CANCELLED:
one per event cancellation

EVENT_UPDATED:
multiple legitimate updates possible

Need exact strategy.

Potential:
events table stores:
- published_event_id
- cancelled_event_id
or operation log/outbox style

But avoid adding many awkward columns if unnecessary.

Alternative:
communication events emitted with deterministic operation keys:
- EVENT_PUBLISHED:{eventId}
- EVENT_CANCELLED:{eventId}
- EVENT_UPDATED:{eventId}:{updatedAt/version}

If using updatedAt:
ensure sufficient uniqueness/stability.

Better:
add optimistic integer `version` to events and use:
EVENT_UPDATED:{eventId}:{version}

Evaluate.

Do not build full outbox in MVP.
