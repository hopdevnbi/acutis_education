==================================================
PART K — IDEMPOTENT HEADER CREATION
==================================================

Critical.

Use:
notifications.operation_key UNIQUE

Logical dedupe:
same operationKey = same logical notification.

applicationEventId:
trace/replay identity also unique.

Handler algorithm:

1. receive event
2. validate event contract
3. resolve recipients
4. create notification header idempotently
5. create missing recipients idempotently

Replay:
same operationKey must not create second header.

Need safely handle DB unique collision race.

Do NOT:
check-then-insert only without unique-error recovery.

Strong design:
attempt insert
-> catch unique violation
-> fetch existing by operationKey
-> continue recipient reconciliation

==================================================
PART L — APPLICATION_EVENT_ID CONFLICT SEMANTICS
==================================================

Possible cases:

A.
same operationKey + same applicationEventId
=> normal replay

B.
same operationKey + different applicationEventId
=> logical replay/redelivery; reuse existing notification

C.
different operationKey + same applicationEventId
=> suspicious contract violation

For C:
do NOT create second header.
Log/report typed conflict internally.

Define:
NotificationEventIdentityConflictError
or safe internal warning.

Do not leak internals to users.
