7. Preferred Pattern — Higher-Layer Orchestration
-------------------------------------------------
If an HTTP route needs data from multiple domain modules:

put orchestration in the module that already depends downstream,
or in a thin application-facing controller/provider owned by the downstream module.

Example:
EnrollmentModule may call:
- StudentService
- ClassService
- StudentAccessService
because EnrollmentModule already depends on StudentModule and ClassModule.

Do NOT make StudentModule import EnrollmentModule just because one student route needs enrollment-backed filtering.

8. StudentAccessService Boundary
--------------------------------
StudentAccessService should own checks based on StudentModule evidence:

- linked student user
- guardian relationship
- student lifecycle

It should NOT query Enrollment repository.

If it needs enrollment-derived access evidence:
prefer one of:

A. caller composes StudentAccessService + EnrollmentQueryService
B. EnrollmentModule exposes a higher-level scoped query endpoint/service
C. StudentAccessService accepts pre-resolved studentIds/context as input

Do NOT create StudentModule -> EnrollmentModule.

9. ClassScopeService Boundary
-----------------------------
ClassScopeService owns evidence from:

- class snapshot
- class catechist assignments
- parish scope delegation

It should NOT depend on EnrollmentModule unless absolutely necessary.

For parent access to a class:
preferred caller-side orchestration can combine:
- StudentAccess/guardian evidence
- EnrollmentQueryService child-class evidence
- ClassScopeService class checks

Do not force reverse module dependency.

10. ParishScopeService Boundary

- ParishModule-owned persistence
- Users/Auth-related safe identity/role context if needed

Do NOT make ParishModule import Student/Class/Enrollment modules.

If parish read access for catechist/parent needs non-parish evidence:
perform that orchestration outside ParishModule.
