13. Student Guardian History Constraint
---------------------------------------
Important audit correction from #001:

The report suggested unique `(student_id, guardian_user_id)` while also preferring a new row after ENDED for audit history.

Those two goals conflict.

Resolve now.

Preferred persistence model:
allow historical re-link rows.

Therefore use FILTERED UNIQUE INDEX:
one ACTIVE guardian link per `(student_id, guardian_user_id)`

Example name:
UQ_student_guardians_student_id_guardian_user_id_active
WHERE status = 'ACTIVE'

Do NOT use permanent unique pair across all history.

This is important.

14. Primary Guardian Constraint
-------------------------------
#001 planned "at most one primary per student" at application layer.

Do NOT enforce in DB in #002 unless a clean filtered unique index is straightforward.

Possible:
unique student_id WHERE is_primary=1 AND status='ACTIVE'

Evaluate.

Preferred:
add filtered unique index if MSSQL supports it cleanly and semantics are stable.

Example:
UQ_student_guardians_student_id_primary_active
ON student_guardians(student_id)
WHERE is_primary = 1 AND status = 'ACTIVE'

This gives strong invariant.

Document decision.
