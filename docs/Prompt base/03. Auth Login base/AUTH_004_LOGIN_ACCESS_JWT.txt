4. Module Boundary — CRITICAL
-----------------------------
Dependency direction:

AuthModule -> UsersModule

AuthModule may import:
- UsersModule
- ConfigModule/framework auth libraries
- its own providers

AuthModule MUST NOT:
- import UserEntity
- inject Repository<UserEntity>
- access users table directly
- import PasswordHashService
- access password_hash

Authentication must call:

UserAccountService.verifyCredentials(...)

or an equally narrow public contract.

UsersModule MUST NOT import AuthModule.

No cycle.

6. JWT Algorithm
----------------
AUTH #001 selected phase-1:
HS256 symmetric JWT.

Keep this decision unless a concrete blocker exists.

Requirements:
- no secret in code
- no default insecure production secret
- algorithm explicitly controlled
- access token short-lived
- signature + expiration verified

Do not add asymmetric keys yet.

9. Access Token Claims
----------------------
Keep access token minimal.

Required:
- sub: user id
- iat
- exp

Do NOT include:
- password hash
- email unless clearly needed
- permissions list
- full roles list
- profile data
- parish/class data

AUTH #001 allowed optional `sid`, but session lifecycle is not implemented yet.

Therefore:
DO NOT include `sid` in #004 unless a session is actually created.

Keep token independent from refresh/session until #005.

10. Authenticated User Context
------------------------------
Define a typed request auth context.

Preferred safe shape:

{
  userId: string
}

Optionally:
{
  sub: string
}

but normalize application-facing form to `userId`.

Do not expose JWT raw payload everywhere.

11. AuthService
---------------
Implement a focused AuthService.

Primary method:
login(email, password)

Flow:

1. call UserAccountService.verifyCredentials(email, password)
2. if invalid:
   return/throw generic unauthorized result
3. if valid:
   sign short-lived JWT access token
4. return safe login response

No user repository access.

12. Login Response
------------------
Preferred phase-1 response:

{
  accessToken: "...",
  tokenType: "Bearer",
  expiresIn: <seconds or stable representation>,
  user: {
    id,
    email
  }
}

Evaluate whether returning user snapshot is useful.

Do NOT include:
- passwordHash
- status unless needed
- roles
- permissions
- refreshToken

Keep response minimal.

13. Login DTO
-------------
Create request DTO.

Required:
- email
- password

Use class-validator.

Do not duplicate full service-layer password policy on login.

Login password input should:
- be string
- have bounded maximum length
- not reveal account creation policy details unnecessarily

Email normalized inside UserAccountService.

Do not expose account state.

17. Public Route Decorator
--------------------------
Evaluate adding:

@Public()

This is useful if a global auth guard is introduced now.

But do NOT introduce a global JwtAuthGuard unless it is clearly beneficial at this stage.

Two valid approaches:

A. Route-level JwtAuthGuard for protected endpoints later
- login naturally public
- @Public not needed yet

B. Global auth guard with @Public
- stronger deny-by-default pattern
- but affects all existing endpoints such as health/swagger

Preferred for #004:
avoid global auth behavior unless carefully justified.

Implement @Public only if the architecture will actively use it now.

No dead decorators.

18. JwtAuthGuard
---------------
Implement reusable JWT access-token guard.

Responsibilities:
- extract `Authorization: Bearer <token>`
- reject missing token on protected endpoint
- verify JWT signature
- verify expiry
- validate `sub`
- attach typed auth context to request

No DB lookup yet unless required.

Authorization/RBAC comes later.

19. Token Extraction
--------------------
Strictly support:

Authorization: Bearer <token>

Reject malformed schemes.

Do not accept token via:
- query string
- cookie
- custom header

Access JWT belongs in Authorization header.

20. User Status After Token Issuance
------------------------------------
Important design question:

If an ACTIVE user logs in and later becomes INACTIVE/LOCKED,
a purely stateless 15-minute access token could remain valid until expiry.

For #004:
document this limitation.

Do NOT add per-request UserModule DB lookup just to solve it prematurely unless clearly justified.

Short access-token lifetime is acceptable for phase 1.
Future hardening may add account-state checks if needed.
