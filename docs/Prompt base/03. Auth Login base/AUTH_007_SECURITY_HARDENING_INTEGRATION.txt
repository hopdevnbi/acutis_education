4. CRITICAL Module Boundary Review
----------------------------------
AUTH #006 currently reports:

- JwtAuthGuard
- AccessTokenService

The report says AccessTokenService was exported so JwtAuthGuard resolves when used on controllers outside AuthModule.

This MUST be independently verified.

In standard NestJS module DI, an exported provider such as JwtAuthGuard should normally be able to use its private dependencies resolved inside AuthModule.

Therefore:

- determine whether AccessTokenService truly needs to be public
- if not necessary, remove it from AuthModule exports
- keep AccessTokenService internal/private
- future business modules should depend only on JwtAuthGuard, not token-signing internals

Preferred final AuthModule public surface:

- possibly other intentionally public auth contracts later

Do not preserve an internal export merely because a test harness was wired incorrectly.

If test modules need auth:
import AuthModule properly.

Add/update architecture tests to prevent accidental export of AccessTokenService.

11. Session Revocation vs Existing Access Tokens
------------------------------------------------
Current AUTH #005 design:
- logout revokes refresh-token family
- access JWT is short-lived
- JwtAuthGuard does not query session DB on each request

Therefore:
a previously issued access token may remain usable until access-token expiry after logout/family revocation.

This is an important design decision.

Audit options:

A. Keep stateless access token:
- accept max ~15 minute revocation delay

B. Add session-active lookup per protected request:
- immediate revocation
- DB query per request
- stronger security but more coupling/load

C. hybrid/cache later

Choose intentionally.

Given this platform can contain minors and administrative capabilities, evaluate whether immediate session revocation is worth the DB lookup.

If implementing session validation:
- DO NOT make JwtAuthGuard directly access AuthSession repository if it breaks boundaries
- use a narrow AuthModule internal/public session validation service appropriately
- avoid exposing persistence
- no cross-module access

If leaving stateless:
document as accepted residual risk for phase 1 and revisit at final audit.

12. Session Validation Semantics
--------------------------------
If access token session-active checking is introduced:

A session referenced by sid should be accepted only if:
- row exists
- not revoked
- not expired (if access session expiry relationship is meaningful)
- belongs to sub user id

But remember rotation:
refresh revokes old auth_sessions row and creates new sid.

This would immediately invalidate the OLD access JWT after refresh.

That may be desirable, but it changes multi-tab behavior.

Audit carefully.

Do not implement without considering:
- refresh rotates sid
- concurrent browser tabs holding old access token
- access JWT lifetime

Document tradeoff.
