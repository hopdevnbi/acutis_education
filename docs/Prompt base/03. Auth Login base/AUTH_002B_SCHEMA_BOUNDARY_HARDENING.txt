3. Why This Prompt Exists
-------------------------
The AUTH #002 report exposed two design mismatches that should be corrected BEFORE service-layer implementation:

A. UUID strategy mismatch

Foundation/AUTH #001 decision:
- UUID v4 generated by application code
- MSSQL `uniqueidentifier`
- do NOT rely on DB-generated identifiers

But AUTH #002 migration currently uses:
- `NEWSEQUENTIALID()` PK defaults

This conflicts with the established architecture.

B. Module persistence exposure

AUTH #002 reports:
- `UsersModule`, `AuthModule`, `AccessControlModule` export `TypeOrmModule`

This can allow other modules to inject repositories/entities owned by another bounded context, which conflicts with the new modular/microservice-ready rules.

Persistence internals must remain module-private.

4. Primary Objective
--------------------
Fix these boundary mismatches while preserving the already-created schema design.

Required outcome:

- UUID generation semantics align with application-generated UUID v4
- no business module exports raw TypeORM persistence infrastructure
- no cross-module repository access becomes possible by default
- migrations remain reversible
- schema remains functionally equivalent
- tests explicitly protect these architectural rules
- no auth business logic is introduced

5. UUID Strategy — Required Final State
---------------------------------------
The permanent project decision is:

- entity IDs are generated in application code
- UUID version 4
- stored in MSSQL `uniqueidentifier`
- DB schema must NOT generate IDs with:
  NEWID()
  NEWSEQUENTIALID()

Review all new AUTH entities:

- UserEntity
- RoleEntity
- PermissionEntity
- AuthSessionEntity

and any other UUID identity columns.

Use the existing project-consistent application generation mechanism.

Preferred:
- `crypto.randomUUID()` via entity field initialization / hook / service-level creation strategy

Choose the cleanest mechanism that works correctly with TypeORM.

Do NOT create a global BaseEntity abstraction.
