6. Refresh Token Format
-----------------------
Do NOT use refresh JWT by default unless there is a concrete reason.

Preferred design:
opaque cryptographically random refresh token.

7. Refresh Token Storage
------------------------
NEVER store raw refresh token.

Store only a cryptographic digest.

Preferred:
HMAC-SHA-256 using a dedicated server secret

or:

Preferred stronger architecture:
HMAC-SHA-256 with dedicated secret:

Do not reuse JWT access signing secret unless strongly justified.

18. Refresh Flow
----------------
Required flow:

1. obtain raw refresh token
2. compute hash
3. locate matching active session
4. reject if:
   - missing
   - not found
   - expired
   - revoked
5. verify associated account still ACTIVE through UserAccountService public API
6. rotate refresh token
7. persist new hash
8. issue new access JWT with same session id
9. return new access token
10. deliver new refresh token through chosen transport

All failures:
generic 401/Unauthorized response.

20. Reuse Detection
-------------------
AUTH #001 requires token family/reuse detection.

Current single-row session model has:
- token_family_id
- refresh_token_hash
- revoked_at

A naive rotation overwrites old hash and loses evidence of previous token.

Audit carefully.

Possible strategies:

A. One row per rotating refresh token
- same token_family_id
- previous row revoked on rotation
- new row inserted
- reuse of revoked token can be detected

B. One session row and separate token history
- requires new table

C. Store previous token hash
- requires new column, limited history

Preferred modular/simple secure design:
One auth_sessions row per refresh-token instance within a token family.

If choosing this:
- each refresh generates a NEW session row/id or token-instance row?
But access-token `sid` semantics must remain clear.

Alternative:
treat `id` as token instance and `token_family_id` as logical browser session family.

Then:
- login: one active auth_sessions row
- refresh: revoke current row + insert new row with same family id
- new access JWT uses new row id as sid
- old refresh token maps to revoked row
- reuse of revoked token triggers family revocation

This is a strong option.

Audit and choose explicitly.

21. Token Family Revocation
---------------------------
If reuse of an already-revoked refresh token is detected:

Revoke all active rows with same token_family_id.

Then reject request.

This limits replay damage.

No user-global logout required yet.
