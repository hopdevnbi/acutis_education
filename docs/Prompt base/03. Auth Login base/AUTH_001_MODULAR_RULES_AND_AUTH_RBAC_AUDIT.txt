4. CRITICAL ARCHITECTURE PRINCIPLE
----------------------------------
The system must be designed as a modular monolith today, but with boundaries that make future microservice extraction practical.

This is a permanent architecture rule.

Every future feature/module must:

- own a clear responsibility
- expose a small public interface
- avoid reaching into another module's internal files
- avoid direct cross-module repository/database access
- avoid cyclic dependencies
- avoid shared "god services"
- avoid global utility dumping grounds
- keep domain concepts inside the owning module
- keep persistence logic close to the owning module
- communicate across modules through explicit exported services/contracts
- minimize infrastructure coupling
- keep controllers thin
- keep business/application logic out of controllers
- keep module-specific DTOs/contracts inside their module unless genuinely shared
- avoid premature shared abstractions

The modular monolith should be extractable later into smaller services with minimal domain rewriting.

5. Add Permanent Rules
----------------------
Update PROJECT_RULES.md with a dedicated section such as:

"Modular Architecture & Future Microservice Extraction"

Required rules:

1. Each major business capability is a separate NestJS module/bounded context.

2. A module owns:
   - controllers
   - application/services
   - entities
   - repositories/data access
   - DTOs
   - guards/policies specific to that capability
   - tests

3. One module must NOT directly import another module's:
   - repository
   - entity persistence internals
   - private service
   - internal DTO
   - internal utility

4. Cross-module interactions must use explicitly exported interfaces/services.

5. Cross-module database queries are prohibited by default.
   The owning module must provide an application-level API.

6. Avoid shared database transaction logic spanning unrelated modules unless truly necessary and explicitly documented.

7. Shared/common code is allowed only for genuinely cross-cutting infrastructure:
   - logging
   - config
   - HTTP errors
   - security primitives
   - generic framework helpers

8. Business/domain logic must NOT be moved to `common/` merely because multiple modules use it.

9. Do not create generic BaseService/BaseRepository/BaseController abstractions for convenience.

10. New module implementation prompts must include a "Module Boundary Audit" section.

11. Every major module final-audit prompt must document:
    - owned data
    - public exports
    - inbound dependencies
    - outbound dependencies
    - possible future service extraction boundary

12. Prefer domain IDs/contracts over passing ORM entities across module boundaries.

13. Avoid exposing TypeORM entities as public API contracts.

14. External integrations should be hidden behind adapters/interfaces when introduced.

15. If an architectural decision creates tight coupling that would make future extraction difficult, it must be documented explicitly.
