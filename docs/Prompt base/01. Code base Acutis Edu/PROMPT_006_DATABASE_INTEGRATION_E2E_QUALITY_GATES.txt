4. Core Principle — Test Isolation
----------------------------------
Automated DB tests must NEVER use the normal development DB:
catechism_api

Create/use a dedicated test database naming convention.

Preferred:
catechism_api_test

or a dynamically unique database derived from that name when concurrency requires it.

The test strategy must prevent accidental writes to:
- development DB
- production DB

Do not rely on developers remembering to change DB_NAME manually.

The automated test command should make the test DB explicit.

5. Choose the Test Database Strategy
------------------------------------
Evaluate and implement the simplest robust strategy for this project.

Preferred direction:
- reuse the existing local MSSQL Docker service
- create a dedicated catechism_api_test database
- integration tests connect only to the dedicated test DB
- test DB can be safely created/reset by test tooling
- normal dev DB is untouched

Possible implementation:
- dedicated integration-test env/config
- helper script to create/drop/reset test DB
- dedicated Jest integration/e2e config
- migration execution before DB tests

Do NOT introduce Testcontainers unless there is a concrete need.
We already have a validated Compose MSSQL runtime.

Avoid adding infrastructure complexity without benefit.

6. Test Database Creation
-------------------------
Create a deterministic mechanism that can:
- create the test database if absent
- drop/reset ONLY the test database when explicitly required
- never drop the normal application DB
- never operate on an arbitrary DB name from unsafe input

Use a hard guard.

For example:
test DB name must end with:
_test

or exactly equal a configured safe test name.

If the name does not satisfy the safety rule:
FAIL immediately.

This guard is mandatory before any destructive database operation.

7. Test Database Environment
----------------------------
Add only the environment/config support necessary for DB integration testing.

Do not pollute production configuration with dangerous flags.

Preferred approaches:
- test-only env file such as .env.test.example
- Jest environment setup
- explicit scripts that export/override DB_NAME for test process

If using .env.test:
- actual .env.test must be ignored
- .env.test.example may be tracked
- no real secrets

Reuse DB host/user/password values safely for local integration tests while ensuring DB_NAME is the dedicated test DB.

Do not introduce DISABLE_DATABASE=true or similar production escape hatches.

13. Database Test Utility Safety
--------------------------------
If adding a Node test DB management script, it must:
- use centralized/config-compatible env parsing where practical
- validate test DB name
- quote identifiers safely
- never concatenate untrusted SQL values into DDL unsafely
- connect to a safe system DB (e.g. master) only for create/drop operations when necessary
- close connections in finally blocks
- produce useful non-secret errors
- never print DB_PASSWORD

14. Test DB Reset Strategy
-------------------------
Choose one predictable lifecycle.

Preferred baseline:
Before DB integration suite:
- ensure test DB exists
- ensure migration state is clean/current

After suite:
- either leave dedicated test DB for speed
or
- clean/drop it

Choose intentionally.

If dropping after tests:
- strict _test guard required
- handle active connections safely

If preserving:
- ensure tests do not become order-dependent
- reset schema/state before each relevant suite

Since there are no business tables yet, keep this simple.

Document future convention for business-module integration tests.

15. Real DB Integration Tests
-----------------------------
Add a focused integration suite.

At minimum validate:

1. Connection
- TypeORM DataSource initializes against MSSQL test DB

2. Server

3. Database identity
- SELECT DB_NAME() equals expected test DB
- proves tests are NOT using development DB

4. Configuration
- synchronize=false
- migrationsRun=false

5. Migration metadata/state
- migration tooling query works
- no unexpected pending migrations / correct current state

6. Cleanup
- DataSource destroys cleanly

These tests must actually run against live MSSQL.
