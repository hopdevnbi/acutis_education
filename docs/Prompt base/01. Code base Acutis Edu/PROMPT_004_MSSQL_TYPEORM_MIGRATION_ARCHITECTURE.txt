6. Database Configuration
-------------------------
Extend the existing centralized configuration architecture.

Do NOT read process.env directly from application/database business code.

Add typed database configuration through the existing:
- @nestjs/config
- Joi validation
- AppConfigService / typed config architecture

Expected environment variables:

DB_HOST
DB_PORT
DB_NAME
DB_USER
DB_PASSWORD

Also deliberately support MSSQL TLS behavior needed for local vs production environments.

Evaluate variables such as:

DB_ENCRYPT
DB_TRUST_SERVER_CERTIFICATE

Recommended semantics:

Production:
- encryption should be supported and safe
- trustServerCertificate should default to false

Local development:
- trustServerCertificate may be configurable because local MSSQL containers often use self-signed certificates

Do not make insecure production defaults just to simplify local development.

Optional pool configuration may be added ONLY if there is a concrete reason.

Avoid speculative environment variables.

12. TypeORM Naming Conventions
------------------------------

15. Migration Architecture
--------------------------
Establish TypeORM migration tooling.

Required capabilities:

- generate migration from entity/schema differences
- create empty migration when deliberately needed
- run pending migrations
- revert the most recent migration
- show/list migration status where supported

Package scripts should provide clear commands.

Examples conceptually:

npm run migration:create -- <name>
npm run migration:generate -- <name>
npm run migration:run
npm run migration:revert
npm run migration:show

The exact implementation must actually work with the chosen TypeORM CLI invocation.

Do not add fake scripts.

16. Migration Source / Build Strategy
-------------------------------------
Design migrations so they work predictably in:

A. local TypeScript development
B. compiled production code

Avoid a setup where:
- development finds .ts migrations
- production accidentally searches only .ts files in dist
or vice versa.

Choose and document a reliable pattern.

For example:
- source migrations under src/database/migrations
- compiled migrations under dist/database/migrations
- DataSource glob handles current runtime extension safely

Be careful not to execute both .ts and .js duplicates.

- Do not create two conflicting configuration systems.

If CLI cannot use Nest DI directly, share pure configuration-building functions safely.

Document the architecture.
