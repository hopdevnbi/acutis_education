3. Primary Objective
--------------------
Create a reliable local Docker development stack for the backend and validate the first real NestJS ↔ MSSQL connection.

This prompt should:

- add Docker support for the NestJS API
- add Docker Compose for local development
- run MSSQL in Docker
- use a persistent MSSQL volume
- add health checks
- create deterministic startup behavior
- configure API-to-MSSQL networking correctly
- support local migrations against the real MSSQL container
- validate real API ↔ MSSQL connectivity
- avoid machine-specific IP addresses
- keep database schema empty except TypeORM migration metadata if migration commands create it
- preserve lightweight public liveness endpoint behavior
- prepare for Prompt #006 integration/e2e tests

Do NOT implement any catechism business entities or tables.

4. Environment / Host Assumptions
---------------------------------
The project must NOT depend on:
- Docker Desktop-specific host integration
- host.docker.internal as a mandatory path
- a developer-specific LAN/Wi-Fi IP
- a WSL-specific hard-coded IP
- localhost for container-to-container database access

Within Docker Compose:
- API must connect to MSSQL using the Compose service name.

Expected concept:
DB_HOST=mssql

Host-side tools such as DBeaver may later connect via the published MSSQL port on localhost if the local environment supports it.

Do not bake host networking assumptions into application code.

5. Dockerfile Strategy
----------------------
Create a Dockerfile suitable for both:

A. local development
B. production-oriented build validation

Preferred approach:
- multi-stage Dockerfile
- explicit Node 22.23.1-compatible image
- dependency install using package-lock.json
- non-root runtime user where practical
- efficient layer caching
- minimal production runtime image

Do not use `latest` Node tags.

Use a pinned image compatible with exactly Node 22.23.1.

If the official Node image tag cannot express the exact patch version cleanly, choose the closest safe pinned form and document the difference clearly.
Do not silently change the project runtime requirement.

6. Local Development Container
------------------------------
The Compose API service should support developer workflow.

Preferred local behavior:
- source mounted into API container
- node_modules handled safely so host/Windows modules do not overwrite Linux container modules
- run NestJS in watch mode
- expose application port to host
- use env file / Compose environment
- connect to MSSQL using service DNS name

Be careful with Windows/WSL bind-mount behavior.

Do not design a setup that requires reinstalling dependencies every file change.

Document any anonymous/named volume used for container node_modules.

8. Docker Compose File
----------------------
Create a clear local Compose file.

Preferred filename:

Do not introduce Redis, message brokers, storage services, or unrelated infrastructure.

9. MSSQL Container
------------------
Use an official Microsoft SQL Server Linux container image appropriate for local development.

Pin a specific supported image tag rather than using a floating latest tag.

Document the image/tag selected and why.

Environment variables should follow the image's current supported convention.

Use a strong local development password supplied through environment configuration.

Do NOT hard-code a real password in:
- Dockerfile
- Compose file
- source
- Git-tracked .env

The existing .env.example may contain only an obvious local placeholder.

10. MSSQL Edition
-----------------
Use an appropriate local/development edition configuration.

Prefer:
ACCEPT_EULA=Y

and a developer-friendly edition such as:
MSSQL_PID=Developer

if supported by the chosen image.

Do not configure production licensing assumptions.

11. Local Credentials
---------------------
Decide a clean local mechanism for MSSQL SA credentials.

Preferred flow:
- .env remains local and ignored
- .env.example documents required values
- Compose consumes the local .env
- same password is used by:
  - MSSQL container
  - NestJS DB_PASSWORD
  - migration CLI

Avoid defining two independent passwords that can drift.

If the MSSQL container requires a variable name different from application DB_PASSWORD, use Compose variable interpolation to map one local secret to both.

Example concept only:
MSSQL_SA_PASSWORD=${DB_PASSWORD}

Do not duplicate secrets in source.

12. Database Name Creation
--------------------------
The configured application database may not exist on first MSSQL container startup.

Design a deterministic, idempotent local database-creation mechanism.

Preferred requirements:

- create DB_NAME if it does not exist
- reruns safely
- waits until MSSQL accepts connections
- does not recreate/drop existing DB on normal startup
- no destructive reset by default
- works with persistent volume

Possible approaches:
- a small init shell script
- a dedicated one-shot mssql-init Compose service
- another clear idempotent approach

Choose the simplest reliable method.

If using an init service:
- it must depend on MSSQL health
- it must exit successfully after ensuring DB exists
- API should not attempt connection until required DB creation has completed, if Compose dependency semantics can guarantee it

Document the decision.

13. SQL Tooling in Init Container
---------------------------------
Be careful about current Microsoft SQL tooling locations.

Do not assume obsolete paths such as:
- /opt/mssql-tools/bin/sqlcmd

without verifying the selected image.

Use the sqlcmd path/tooling actually available for the chosen MSSQL image or explicitly use a separate tools container if required.

Document the exact command/path.

14. CRLF / Shell Compatibility
------------------------------
This project may be developed on Windows/WSL.

Any shell scripts added for Docker must be safe from CRLF issues.

Requirements:
- store shell scripts with LF endings
- use a valid shebang
- use `set -e` / `set -eu` / `set -euo pipefail` only when supported by the chosen shell
- do not accidentally execute bash-specific syntax under /bin/sh

Add repository/editor normalization only if necessary and within scope.

If introducing .gitattributes for LF enforcement on shell scripts, document it.

15. Persistent MSSQL Volume
---------------------------
Use a named Docker volume for MSSQL persistence.

Example concept:
mssql-data

Mount the correct Microsoft SQL Server data path.

Do not use a host-specific absolute Windows/WSL path.

Normal:
docker compose down

should preserve DB data.

Only:
docker compose down -v

should remove the development DB volume.

Document this clearly.

16. MSSQL Port Publishing
-------------------------
Publish MSSQL to the host for local tools such as:
- DBeaver
- sqlcmd from host
- debugging

Avoid collisions with a native Windows MSSQL instance.

Do NOT blindly force:
1433:1433

if the developer may already have native MSSQL running.

Introduce a configurable host publish port, e.g.:

MSSQL_PUBLISH_PORT=14330

with a sensible non-conflicting default.

Inside Docker:
DB_PORT remains 1433.

Outside Docker:
host tools use localhost:${MSSQL_PUBLISH_PORT}.

Add this variable to .env.example if used.

17. API Port Publishing
-----------------------
Publish the API using current PORT semantics.

Avoid ambiguous dual use if PORT is both container listen port and host publish port.

A simple same-port mapping is acceptable for local development.

If introducing:
APP_PUBLISH_PORT
or equivalent,
only do so if it improves clarity.

Avoid unnecessary config growth.

18. MSSQL Health Check
----------------------
Add a real container health check for MSSQL.

It should verify that SQL Server is actually accepting SQL connections, not merely that the process exists.

Requirements:
- reasonable interval
- reasonable timeout
- enough retries/start period for MSSQL cold boot
- credential handling must not leak unnecessarily into logs

Do not use a fake TCP-only check if sqlcmd connectivity can be used reliably.

19. API Health Check
--------------------
Add an API container health check using the existing:

GET /api/v1/health

Keep this endpoint as application liveness only.

It should NOT be changed to fail because MSSQL is unavailable.

If a container health command requires curl/wget and the base image lacks it:
- prefer a Node-based healthcheck
or
- install only the minimal required package intentionally

Avoid unnecessary OS packages.

20. Startup Ordering
--------------------
Compose startup should be deterministic.

Expected logical order:

1. MSSQL starts.
2. MSSQL becomes healthy.
3. Local application DB is ensured/created.
4. API starts and connects to the configured database.

If using mssql-init:
- depend on MSSQL health
- API may depend on init service successful completion

Use current Docker Compose dependency conditions supported by the environment.

Do not rely only on arbitrary sleep timers.

A small retry loop inside init may still be acceptable as a defensive measure, but health/dependency semantics should be primary.
