5. Configuration Module
-----------------------
Introduce NestJS configuration support using an appropriate stable package compatible with NestJS 11.

Preferred direction:
- @nestjs/config

Requirements:
- Load environment variables centrally.
- Do not read process.env throughout business/application code.
- Validate environment variables at startup.
- Fail fast on invalid required configuration.
- Preserve strong typing as far as practical.
- Avoid an over-engineered custom configuration framework.

At this stage, define only configuration actually needed by the current foundation.

Expected baseline values include concepts such as:
- NODE_ENV
- PORT

Do NOT invent:
- DB credentials
- JWT secrets
- storage credentials
- SMTP configuration
- Redis configuration
- external APIs

Those should be introduced only when their modules arrive.

6. Environment Schema / Validation

Evaluate a stable validation approach compatible with the current stack, for example:

- sensible defaults may exist for local development where appropriate.
- production behavior must not silently accept malformed values.

Do not use unsafe casts merely to satisfy TypeScript.

10. Global Exception Handling
-----------------------------
Implement a centralized exception filter / error response contract.

Goals:
- all API errors should eventually have a predictable structure
- known Nest HTTP exceptions should preserve the correct HTTP status
- unexpected exceptions should return HTTP 500 without leaking stack traces/internal details
- unexpected exceptions should be logged
- response should include the request/correlation ID
- error payload should be safe for clients

Define a simple initial error schema.

A reasonable conceptual structure could include:
{
  "statusCode": 400,
  "error": "Bad Request",
  "message": "...",
  "path": "/api/v1/...",
  "timestamp": "...",
  "requestId": "..."
}

However, do not mechanically copy this if NestJS validation errors require a better structured message representation.

Important:
- preserve useful validation error details
- never expose stack trace
- never expose raw SQL/internal errors in future
- do not catch/rethrow everywhere
- centralize behavior

Create explicit TypeScript types/interfaces for the public error contract where useful.

11. Request / Correlation ID
----------------------------
Introduce a request ID/correlation ID mechanism.

Requirements:
- Every incoming HTTP request receives a stable request ID.
- If a safe incoming request ID header is supported, validate/normalize it before trusting it.
- Otherwise generate a UUID using a secure built-in approach where possible.
- Make the ID available to:
  - structured logs
  - global exception responses
  - response headers if appropriate
- Avoid global mutable state that can leak request context across concurrent requests.

Keep this implementation simple.

Evaluate whether:
- middleware
- AsyncLocalStorage
- logger request context
or another Nest-friendly mechanism is appropriate.

Do not introduce a large context framework without need.

Document the decision.

12. Structured Logging
----------------------
Replace ordinary scattered/default logging behavior with a deliberate structured logging baseline.

Evaluate a stable NestJS-compatible approach.

Preferred characteristics:
- JSON structured logs
- request-aware logging
- request ID included automatically
- log levels
- production friendly
- readable enough for local development
- no secrets or entire sensitive bodies logged
- compatible with future containerized environments

A package such as:
- nestjs-pino / pino
may be considered if compatible with NestJS 11 and the project rules.

Do NOT add a logging package blindly.
Check compatibility and use a maintained stable version.

Requirements:
- no console.log in application code
- log application startup
- log unexpected exceptions
- HTTP request logs should not expose sensitive request bodies
- avoid logging Authorization, Cookie, or similar secrets
- establish redaction for sensitive headers/fields if the chosen logger supports it

If local pretty logging requires an optional dev-only dependency, keep production output structured and document the choice.

13. Logging Privacy / Redaction
-------------------------------
At minimum, explicitly protect sensitive fields/headers such as:
- authorization
- cookie
- set-cookie
- password
- token
- accessToken
- refreshToken

Because this platform will eventually contain minors' information, default toward minimal request logging.

Do not log complete request/response bodies globally.

14. Swagger / OpenAPI
---------------------
Add Swagger/OpenAPI using packages compatible with NestJS 11.

Preferred package:
- @nestjs/swagger

Requirements:
- Swagger should describe API version/title/basic metadata.
- Swagger UI should be available at a predictable path such as:
  /api/docs
or another well-justified path.

Important:
The API itself remains under:
  /api/v1

Do not accidentally make Swagger route:
  /api/v1/api/docs

Choose and document the route clearly.

Swagger should be enabled by environment/configuration rather than assumed to be publicly available in every production deployment.

Suggested behavior:
- enabled by default for development
- disabled by default or explicitly configurable for production

Choose a small config variable if required, e.g.:
SWAGGER_ENABLED

If introduced:
- add it to config validation
- add it to .env.example
- make boolean parsing predictable

Do not add auth schemas yet because authentication does not exist.
